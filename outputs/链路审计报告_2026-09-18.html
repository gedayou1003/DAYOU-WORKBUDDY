二、P0 · 三个真 BUG

P0-1已交付报告里的数字错误：偏差表「本期变化」基期取错

位置：outputs/作战报告_晨报_2026-09-18.md 第 211 行

报告原文：「样本 49→50 期。方向 ⚠️ +1（56.2%→56.0%）；区间 ✅ +1（36.7%→38.0%）」

实测三期的真实值（从历次报告提取）：

报告期数 n方向 ✅/⚠️/❌方向纯命中率区间纯命中率
9/17 晨报4827 / 17 / 456.2%—
9/17 收盘4928 / 17 / 457.1%36.7%
9/18 晨报（本份）5028 / 18 / 456.0%38.0%

问题：同一句话里两个维度的对比基期不一致 ——

  • 方向用了 56.2%（9/17 晨报，n=48） 作基期 → 取成了上上期，正确应为 57.1%（9/17 收盘，n=49）；
  • 区间用了 36.7%（9/17 收盘，n=49） 作基期 → 这个是对的。

两处基期一个 48 期、一个 49 期，与同句声明的「样本 49→50 期」也对不上。

修法：把该句改为「方向 ⚠️ +1（57.1%→56.0%）」。
根因：这段是手写文本，而统计表本身是 chainlib.bias_stats() 程序生成的（已复核，与报告表格 28/18/4、n=50、56.0% 完全一致 ✓）。即：表格可信、叙述不可信。
建议：把「本期变化」也改为程序生成（对比上一期快照），或至少在 check_layout.py 里加一条断言：报告正文出现的「上期值」必须等于上一份报告的对应单元格。

P0-2抓取失败仍退出 0，且用残缺结果覆盖原始快照（数据不可恢复）

位置：.workbuddy/fetch_zsxq.py 第 299–311 行

out = .../zsxq_fetch_raw.json with open(out, "w", encoding="utf-8") as f: # ← 无条件覆盖，不判断本轮成功率 json.dump(results, f, ensure_ascii=False, indent=1) ... if auth_failed: print(f"COOKIE_AUTH_FAILED={len(auth_failed)} (gid: ...) → 需更新 .../zsxq_cookie.txt") print(f"SAVED={out}") # ← 然后正常结束，退出码 0

后果链（全部实测确认）：

  1. Cookie 通道失效时，6 个 Cookie 星球全部取不到数据 → results 只剩 Skill 通道的 3 个星球；
  2. 脚本仍然写文件、仍然打印 SAVED=、仍然退出 0 → 调用方（我 / 手动执行）无法分辨「抓成功」与「抓残了」；
  3. 该文件既不在 git 跟踪列表（已用 git ls-files 确认），也在备份脚本的排除清单里（export_backup.py 的 EXCLUDE_SUFFIX 含 zsxq_fetch_raw.json）→ 一旦被覆盖，上一轮完整快照无法恢复。

注：脚本已区分「真失效（401）」与「限流抖动（HTTP 200 但 succeeded=false）」并分别计数上报（COOKIE_AUTH_FAILED / COOKIE_FLAKY_FAILED）——分级做对了，缺的只是最后一步「按计数决定退出码」。

修法（两处，都很小）：
  1. 加退出码：main() 末尾 return 2 if auth_failed else (1 if flaky_failed else 0)，并在 __main__ 里 sys.exit(main())；
  2. 加写入守卫：若 results 为空、或 auth_failed 非空，则写入带日期后缀的旁路文件（如 zsxq_fetch_raw_2026-09-18_partial.json）而非覆盖主快照，并在 stderr 明确提示「主快照未更新」。

P0-3归档脚本无「0 条守卫」，会把当天归档覆盖成空

位置：.workbuddy/gen_tj_archive.py 第 76–80 行

out = os.path.join(ROOT, 'outputs', f'DRAGON_BALL_原始记录_{today}.md') with open(out, 'w', encoding='utf-8') as f: # ← 无条件覆盖，文件名按日期固定 f.write(md) print(f"DRAGON BALL模型 归档完成，{len(tj)} 条 -> {out}") # ← 0 条也报「完成」，退出 0

与 P0-2 联动：上游快照被写残（或目标星球本轮恰无新帖）时，本脚本会把当天的归档文件重写为「本期共 0 条」并显示「归档完成」；而 outputs/ 不在 git 里 → 当天已归档的原文无法恢复。

修法：
  1. len(tj) == 0 时不覆盖已有文件：若目标文件已存在则跳过并 stderr 告警，退出码非零；
  2. 写入改为「先写临时文件 → 校验条数 > 0 → 原子替换」；
  3. 顺带：头部「抓取通道：zsxq-cli Skill」是写死的，而实际是双通道（Skill + Cookie 回退）→ 改为按数据来源生成。

三、P1 · 四项框架性技术债

P1-1校验器退出码无 ERROR/WARN 分级 + 静态初验变成永久告警

位置：.workbuddy/check_integrity.py 第 192 行 return 2 if problems else 0

问题：既定约定是 0 通过 / 1 有 ERROR / 2 有 WARN（check_layout.py 与 check_display_name.py 都正确实现了）。但 check_integrity 任何问题都返回 2 → 无法区分「链断档」（严重）与「1 条 review 缺字段」（轻微）。

更值得改的是噪声：按既有机制，晨报档会对前一日收盘档做开盘前静态初验，此时该条 review.actual 本就不含 OHLC（刻意为之）。但【5】把它计入 problems 并打 ⚠️ → 每个晨报档都会固定报同一条告警，今天的结果就是「数据异常 1」。而项目笔记里应对办法是「先确认是不是静态初验的预期状态」—— 靠人脑排除噪声，正是闸门失效的标准路径。

修法：
  1. 新增识别：review.phase 含「静态初验」或四维中有 support/resistance 判定但 actual 无 OHLC → 该条降为 INFO（明示「待收盘补判」），不计入 problems；
  2. 引入 ERROR/WARN 两级计数，返回 1 if errors else (2 if warns else 0)；
  3. 把分级口径写进 脚本地图.md（目前该约定只在记忆里）。

P1-2文档三胞胎：同一批脚本被三份文档各描述一遍 → 已产生 41 处失效引用

三份文档的重叠：脚本地图.md(29 KB) / 报告生成流程.md(10 KB) / README_预判系统.md(8 KB)。实测被两份以上文档重复描述的脚本 17 个（fetch_zsxq / get_daily_ohlc / analyze_000001_multi / check_layout 各被 3 份描述）。

代价已兑现：扫描文档中引用的 *.py 共 41 处指向不存在的文件，其中 13 处指向的是已经归档的脚本（update_chains.py、append_consensus.py、gen_evening_report.py、gen_intraday_svg.py、_tech_extra.py、_audit_layout.py、_calc_boll.py …全部已在 .workbuddy/archive/），另有 5 处是真失效名（zsxq_api.py、chan_signal.py、run_000001.py…）。

（另 2 处 run_000001_chansignal.py / run_000001_boll_chan.py 实际存在于技能目录 chan-signal__skillhub/，不算失效，但文档未标注它们是技能内脚本 —— 这也是误判来源。）

修法：
  1. 定一份权威：脚本地图.md 作为唯一「脚本清单」来源，另两份只写流程并链接过去，不再逐脚本复述；
  2. 给脚本地图加「状态列」（✅在用 / 📦已归档 / 🔧技能内），归档时同步改这一列；
  3. 加一条守卫（可并入 check_display_name.py 同级的 check_docs.py）：扫描文档里的 *.py 引用，不存在且不在技能目录 → 报 WARN。

P1-3review 两代字段长期并存：兼容逻辑散落 6 处，漏写即静默少算

实测代际分布（50 条 verified）：

字段代际条数读法
新一代20review.direction_verdict
老一代30review.direction（无 _verdict 后缀）

chainlib.py / chain_apply.py / build_dims_data.py / engine_effectiveness.py / report_builder.py 都写了 rv.get(k+'_verdict') or rv.get(k) 兼容；但 normalize_verdicts.py 只读新代字段。

本轮实证：我写审计探针时只读了 direction_verdict，得到「只有 20 条有判定、30 条缺失」——差点错报成「30 条被静默排除」。这说明该兼容口径对任何新脚本都是陷阱。

修法：把兼容读法下沉为 chainlib.get_verdict(record, dim) 单一出口，禁止其他脚本直接 rv.get('direction_verdict')；或做一次性 normalize_verdicts.py --apply 把 30 条老记录回填成新字段，让代际消失（更彻底，需先备份链）。

P1-4退出码语义缺失 + str.index 裸崩溃（report_builder 类）

位置：.workbuddy/report_builder.py 第 187–191 行、第 199–213 行

def main(): if not os.path.exists(SRC_MD): print(f'❌ 原始晨报不存在：{SRC_MD}') return # ← 打印 ❌ 但 return None → 退出码 0 ... b1_start = md.index('## 第一块'); b1_end = md.index('## 第二块') # ← 缺章节即抛 ValueError（裸崩溃）

五、排版与读感（以 9/18 晨报为样本逐段实测）

先说结论：结构是好的（五块 + 附录 + 产物清单、关键位唯一落地、一眼能看到方向/区间/剧本）。问题集中在「长文本塞进表格单元格」和同一结论的多次复述。

5.1 表格宽度：三处长文本单元格被挤成竖条

位置单元格字数问题
第二块「上期共识复盘」第 3 列「说明」≈110 字/格 × 5 行在 880 px 宽的 HTML 里会被压成窄条，5 行挤在一列
第五块「做多榜 TOP3」「规避榜 TOP3」的「依据」列≈200 字/格本期最严重——一堆产业逻辑塞进一格
附录 A 抓取通道表「备注」列≈90 字/格同因；且备注里混着「本条要点」与「通道状态」两种信息
改法：把这三个长文本列从表格里拆出来，改「分章列表式」——与既有的「对立观点区块改用分章列表式」是同一原则，项目已有先例，直接沿用即可。表格只留「可对比的短字段」（行业 / 涨跌幅 / 方向分 / 置信度），长依据下沉为表下的 - **对象**：依据… 列表。

5.2 信息重复：同一结论出现 4–10 次

结论出现次数分布
「60F 中轨 = 唯一否决点 / 行情强弱分界」≈10 处速览、第一块、第三块定性、第四块置信度、纪律 1、开盘观察 1、关键位表
「隔夜三项反向变量（纳指 +1.7% / 10Y -7bp / WTI 两连跌）」≈8 处速览、上期共识复盘、总体、上期复盘方向行、一句话预判、附注一、纪律 5
「15F 带宽 0.65% 收口 → 变盘在即、方向未定」4 处第三块表、第三块正文、置信度、v5 打分明细

报告自己声明的原则是「信息原子唯一落地」（价格 ≤ 8 次），但该原则目前只约束价格，不约束结论；而结论层的重复反而是读者最疲劳的地方。

改法（不删信息，只改朝向）：速览三行后各加一个指针（如「→ 详见第三块」，需要时的展开处），把重复的解释收敛到首次出现处，后续只做引用（「见第三块」）。
另外：把「同一价位 ≤ 8 次」这条硬指标纳入 check_layout.py 自动校验（现在只校验块/错位/语义），顺带把「同一短语重复 ≤ N 次」也加上——这条是可机器验证的，靠人写容易飘。

5.3 术语与口径的一致性

问题实例
同一对象两种写法30F55（第 281 行）vs 30F MA55（第 164 行）—— 全篇 55 线体系混用「xx55」与「xx MA55」
同一数值两个名字日线 MA20 与日线 BOLL 中轨 都是 3922.09（数学上本相等），报告里三处分别叫「日线 MA20 / BOLL 中轨」「日线中轨」「MA20」
取整口径不透明区间上沿写 3896，关键位表里对应值是 3895.75（30F55）；第 189 行算「距上沿 -20.40 点」用的是 3896。整数与精确值混用，读者无法复算
表格语义被破坏「关键位相对现价」表里插了一行「现价 3875.60」，其「属性」列填「—」——它不是关键位，却占了关键位表的行
改法：① 55 线体系统一写 MA55（含 30F/60F/15F/5F/120F）；② BOLL 中轨与 MA20 同时出现时，只保留一个名字并在表下注一次「BOLL 中轨 ≡ MA20」；③ 区间上下沿统一给精确值（3895.75），整数近似只用于速览；④ 把「现价」行移出关键位表，改为表头下方一行说明。

5.4 附录 A 与附录 B 口径不一致

附录 B 列出 10 个星球，附录 A 只列 7 行（6 个有数 + 短评 0 条）。信息平权 / 投行圈子 / 口罩哥三个星球在 A 里完全没出现，也没有一句「本期未覆盖」——读者会以为漏抓。

改法：附录 A 补一行「本期未覆盖：星球⑧⑨⑩（通道未返回数据 / 未配置）」并在数据完整性说明里点明。

5.5 校验器覆盖面的一个盲区

check_layout.py 只校验每个档位最新一份报告（本次 5 份：晨报 9/18、午间 9/8、盘中 9/3、收盘 9/17、复盘 9/15）。今天晨报确实在列 ✓。但若某天出现「链已写、报告 md 没生成」的中间态，两份校验器都会报绿（check_integrity 查的是链，不是报告文件）→ 漏产报告不会被拦下。

改法：给 check_integrity 加一条【7】当日产物存在性断言：按当日已有的链记录，检查对应 outputs/作战报告_<档位>_<日期>.md 是否存在，缺失即 ERROR。
